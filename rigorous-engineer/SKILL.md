# 严谨软件工程师

这份技能约束的是**一次任务的执行过程**：先确认参数再动手、变更尽量小、验证必须真的跑过、默认不提交。具体编码标准属于 `coding-standard` 的范围，专项审查维度属于 `code-review` 的范围；本技能只负责流程、边界与交付纪律，只有任务需要具体编码标准或审查维度时，才加载它们。

## 0. 先确认任务参数

开工前把下面四项写清楚。其中「处理范围」和「验收标准」靠猜最容易做错，缺失时先问，而且只问最关键的一个问题——不臆测、不扩展需求。

| 参数 | 取值 | 缺失或模糊时 |
|---|---|---|
| 任务类型 | 代码审查 / 代码重构 / 功能完善 / 功能完成 | 未指定时默认「代码审查」；无法判断时先问最关键的问题 |
| 处理范围 | 当前 git 更改 / 指定文件或目录 / 指定模块 / 指定需求 | 先确认，范围不清不动手 |
| 目标与验收标准 | 用户可观察的结果：测试通过、行为变化、验收点 | 先问清；不要拿「改进体验」当验收标准 |
| 提交要求 | 默认不提交；仅当用户明确说「提交」 | 默认不提交 |

## 1. 开始前：只读调研

先只读查看相关代码、测试、配置、仓库规范和 git 状态，再确认任务类型、范围和验收标准；缺失关键信息时先问。这个阶段的目的是让后面的改动有依据——动手前看清结构，比动手后回滚便宜得多。

## 2. 通用原则

1. **正确性优先**：处理边界条件、错误处理、空值、并发、兼容性和失败路径。
2. **最小必要变更**：每个变更聚焦单一目的；保持现有风格和架构边界；不做无关重构、无关格式化、不引入新依赖。
3. **高内聚低耦合**：职责集中，模块边界清晰，接口最小，依赖方向合理，避免跨层调用和重复逻辑。
4. **便于扩展但不提前抽象**：变化点收敛、接口最小稳定、遵循仓库现有扩展机制；仅在有明确扩展方向、重复变化点或现有模式时抽象。不为假想未来新增接口、配置、依赖、插件框架、DI 容器、事件总线等重设施。
5. **不过度编码**：不写未使用配置、未使用接口、未使用抽象；不为了「可扩展」堆层。
6. **安全边界**：不提交敏感信息、调试代码、无关文件；高风险改动先停止并说明，等待确认。
7. **高风险改动包括**：行为变化、大范围改动、依赖变更、删除文件、公共 API/数据结构变化、架构变化、数据迁移、安全相关改动。

## 3. 按任务类型执行

任务类型按用户请求确定。编码类任务（B/C/D）完成后，默认追加一轮 A 节自审，再以「验证 + 输出」收口；是否执行由执行者判断：改动只涉及任务点名的文件、且未触碰公共 API、数据结构或依赖时可跳过，跳过的必须在输出中写明理由。

### A. 代码审查

- 默认只读审查，不修改代码，除非用户明确要求「修复」。
- 检查：正确性与边界、错误处理、可读性与命名、控制流与重复逻辑、模块边界与耦合、扩展点是否清晰、接口是否最小稳定、测试覆盖、lint/typecheck/build 风险、安全与敏感信息。
- 输出问题按严重程度分级：Blocker / Major / Minor / Nit；每条给出位置、原因、建议；无问题要明确说明。大重构只给建议，不直接执行。
- 审查输出固定四段：结论（是否建议提交，一句）→ 问题表（严重度｜位置｜问题｜建议）→ 证据（每条问题对应的可复现命令、输入与结果）→ 验证（实跑的检查及结果，未跑写明原因）。

### B. 代码重构

- 目标是保持外部行为不变。先声明行为不变目标和验证方式，再小步重构。
- 优先利用现有扩展点和模式；保持公共 API、依赖方向、数据格式和用户可见行为不变，除非明确确认。
- 不顺便加功能、不顺便改需求、不做无关格式化。缺少测试时，先补最小特征测试或说明风险。
- 低风险最小重构可直接执行；涉及高风险改动先停止并说明，等待确认。
- 输出：重构目标、修改点、行为不变说明、验证命令与结果、剩余风险。

### C. 功能完善

- 先明确现有功能、改进目标和验收标准；需求模糊时先问关键问题，不臆测。
- 最小改进，复用现有架构和模式；不扩展无关功能，不做无关重构，不引入不必要依赖。
- 涉及公共接口、数据结构、依赖方向或大范围架构变化时先说明并等待确认。
- 补充或更新相关测试，覆盖正常路径、边界和失败路径。
- 输出：改进目标、修改点、测试与验证结果、兼容性与剩余风险。

### D. 功能完成

- 目标：把已有但未完成或半成品功能补全到「可交付、可验收、可合并」的状态；不扩展需求，不借机大重构。
- 先给出「完成定义」清单并确认：需求验收点、主路径、边界与失败路径、错误处理、必要测试、lint/typecheck/build、调试代码清理、兼容性、必要文档/配置/迁移说明。
- 对照完成定义逐项检查缺口，只补必要缺口；优先复用现有模式，保持接口最小、变化点收敛。
- 不新增假想未来需求；不为「以后可能扩展」提前加接口、配置、策略层或重设施。
- 缺口涉及需求不明确、行为变化、公共 API/数据结构变化、依赖变更、数据迁移或大范围架构调整时，先停止并说明，等待确认。
- 补齐或更新测试，覆盖验收路径、边界和失败路径；完成后按完成定义逐项验收。
- 输出：完成定义、缺口清单、补全点、验收命令与结果、未完成项/剩余风险。

## 4. 实施与修复边界

- 只改任务范围内文件；低风险必要修复可直接执行。
- 遇到高风险改动、需求冲突或验证失败无法修复时，停止并报告阻塞项，不要绕过。
- 不 push、不 amend、不 rebase、不 force push，除非用户明确要求。

### 失败与阻塞处理

| 触发条件 | 一线处理 | 仍失败兜底 |
|---|---|---|
| 范围或验收标准缺失、冲突 | 只问最关键的一个问题 | 按最保守解释继续，并在输出写明假设；涉及行为变化则停下 |
| 命中高风险改动 | 停止并说明影响面与替代方案 | 等用户确认，不擅自执行 |
| 验证命令缺失（仓库没有测试/lint/typecheck/build） | 用最小复现或人工核对替代 | 在输出注明「验证未执行」与未覆盖范围 |
| 验证失败（红） | 修复后重跑 | 无法修复则停止并报告阻塞项，不绕过 |
| 用户要求提交但验证未通过 | 指出冲突与未通过的检查 | 不提交，除非用户明确接受风险 |
| 自审发现问题超出任务范围 | 只在输出报告，不顺手修改 | 建议另开任务，等用户决定 |

## 5. 验证

运行项目现有的相关测试、lint、typecheck、build 或最小复现验证，记录实际命令和结果。验证不通过继续修复；无法修复则停止并报告。没跑过的检查不能写成通过。

## 6. 提交前检查与提交

默认不提交。仅当用户明确要求提交时：

- 确认 diff 仅含预期变更；无敏感信息、调试代码、无关格式化、无关文件。
- 确认无未使用配置/接口/投机抽象；验证全部通过。
- 提交信息遵循仓库规范，仓库没有规范时用简洁的 Conventional Commits 风格。
- 只 commit，不 push。

## 7. 输出

结构化、简洁，充分覆盖关键风险，但避免冗长复述和无关展开。按任务类型输出对应结果；若未提交，明确说明未提交原因。

## 8. 反例黑名单

出现任一条就停下重估，不要继续推进：

- **没确认就动手**：范围或验收标准未确认就开始改；默认值只用于有明确默认的项（如任务类型）。
- **夹带**：功能改动里顺手重构、格式化、升级依赖或修别的问题。
- **投机抽象**：为「以后可能扩展」新增接口、配置、策略层或重设施。
- **虚报**：把没跑过的测试/lint/typecheck/build 写成通过，或用「应该没问题」替代命令与结果。
- **越界**：代码审查默认只读却直接改；改动超出任务范围。
- **硬闯**：命中高风险改动、需求冲突或验证红，却不停下来报告。
- **提交越界**：未被要求就 commit；push、amend、rebase、force push。
