# 重构编码规范

> 基于 Martin Fowler《重构：改善既有代码的设计(第2版)》提炼。适用于任何语言和框架。

## 能力

- 识别 24 种代码坏味道，定位需要重构的信号
- 匹配 61 种经过验证的重构手法（编号 106-399）
- 输出不改变外部行为的改进建议，只改善内部结构

## 使用场景

- **代码审查时**：对照坏味道清单审查代码，给出具体重构建议
- **编写新代码时**：主动检查是否引入坏味道
- **修改现有代码时**：添加功能前先做预备性重构
- **用户要求重构/优化时**：识别坏味道并应用对应手法

## 工作流程

### Step 1: 嗅探坏味道

对照"代码坏味道检查清单"，识别代码中的问题信号。

### Step 2: 确定重构手法

根据坏味道类型，从"重构手法速查"或附录速查表中选取合适的重构手法。优先选择编号小的手法（编号越小越基础）。

### Step 3: 实施重构

1. **两顶帽子**：添加功能时不重构，重构时不添加新功能
2. **小步快跑**：步子小到"不可能出错"，每次修改后立即测试
3. **三次法则**：第一次直接做，第二次容忍重复，第三次必须重构
4. **营地更干净**：每次经过代码时让它比到达时更干净一点

### Step 4: 验证

- 重构不改变可观察行为，测试全部通过才算成功
- 如果测试失败且无法快速定位，回滚到最后一次可工作的提交

## 一、重构核心原则

### 1.1 两顶帽子

| 帽子 | 行为 | 禁止 |
|------|------|------|
| **添加新功能** | 只添加新功能，不修改既有代码 | 不重构 |
| **重构** | 只调整代码结构，不添加新功能 | 不添加测试（除非发现遗漏），不修改功能 |

### 1.2 何时重构

| 时机 | 说明 |
|------|------|
| **预备性重构** | 添加新功能前，先重构使功能更容易添加 |
| **帮助理解的重构** | 阅读代码时，通过重构把理解植入代码 |
| **捡垃圾式重构** | 每次经过代码时把它变好一点点 |
| **长期重构** | 大规模重构分散到数周，每次有人靠近"重构区"就推动一点 |

**不应重构的情况**：不需要修改的凌乱代码（容忍它）；重写比重构更容易时。

### 1.3 核心原则

| 原则 | 说明 |
|------|------|
| **YAGNI** | 你不会需要它。只根据当前需求构造软件，同时保持设计质量 |
| **三次法则** | 事不过三，三则重构 |
| **命名即设计** | 想不出好名字说明背后可能潜藏着更深的设计问题 |
| **命令-查询分离** | 有返回值的函数不应产生副作用 |
| **不可变性优先** | 可变数据是最大的错误源头之一，优先使用不可变数据 |
| **性能靠度量** | 90% 的性能问题源于 10% 的代码，用度量工具而非臆测找热点 |

### 1.4 测试原则

| 原则 | 说明 |
|------|------|
| **自动化检查结果** | 测试自动对比期望值与实际值，不靠人眼 |
| **频繁运行** | 正在处理的代码每隔几分钟运行测试 |
| **夹具隔离** | 每个测试创建独立夹具，避免测试间共享数据 |
| **边界条件探测** | 空集合、0 值、负数、空字符串——集中火力攻击边界 |
| **风险驱动** | 测试重点是可能出错的地方，不追求完美覆盖 |
| **先写测试后改代码** | 为既有代码添加测试时：① 先随便填期望值 → ② 用真实值替换 → ③ 故意引入错误验证 → ④ 恢复正确逻辑 |

## 二、代码坏味道检查清单（24种）

### 2.1 命名相关

| 坏味道 | 说明 | 处理手法 |
|--------|------|----------|
| **神秘命名 (3.1)** | 变量/函数/类名无法清晰表达功能和用法。想不出好名字说明背后可能潜藏着更深的设计问题 | 改变函数声明(124)、变量改名(137)、字段改名(244) |

### 2.2 结构相关

| 坏味道 | 说明 | 处理手法 |
|--------|------|----------|
| **过长函数 (3.3)** | 关键不在于长度而在于"做什么"与"如何做"之间的语义距离。每当需要注释来说明什么，就应提炼 | 提炼函数(106)、以查询取代临时变量(178)、引入参数对象(140)、分解条件表达式(260) |
| **过长参数列表 (3.4)** | 参数超过 3 个时应警惕 | 以查询取代参数(324)、保持对象完整(319)、引入参数对象(140)、移除标记参数(314)、函数组合成类(144) |
| **过大的类 (3.20)** | 单个类做太多事，字段和代码太多，导致重复代码 | 提炼类(182)、提炼超类(375)、以子类取代类型码(362) |

### 2.3 重复与冗余

| 坏味道 | 说明 | 处理手法 |
|--------|------|----------|
| **重复代码 (3.2)** | 同一类中相同表达式、不同子类中相同函数 | 提炼函数(106)、移动语句(223)重组后提炼、函数上移(350) |
| **重复的 switch (3.12)** | 不同地方反复使用同样的 switch/if-else，增加分支时须逐一更新 | 以多态取代条件表达式(272) |
| **循环语句 (3.13)** | 传统 for/while 应被管道操作（filter/map/reduce）取代 | 以管道取代循环(231) |
| **冗赘的元素 (3.14)** | 函数名与实现一模一样、类只剩一个函数 | 内联函数(115)、内联类(186)、折叠继承体系(380) |
| **夸夸其谈通用性 (3.15)** | "总有一天需要做这事"——为不会发生的场景准备的钩子和特殊情况 | 折叠继承体系(380)、内联函数(115)、内联类(186)、改变函数声明(124)去参、移除死代码(237) |

### 2.4 耦合与内聚

| 坏味道 | 说明 | 处理手法 |
|--------|------|----------|
| **依恋情结 (3.9)** | 函数跟另一个模块交流频繁远胜于自己模块。原则：谁拥有数据最多，函数就和数据在一起 | 搬移函数(198)、提炼函数(106)+搬移 |
| **数据泥团 (3.10)** | 相同的三四项数据总是结伴同行，应拥有自己的对象 | 提炼类(182)、引入参数对象(140)、保持对象完整(319) |
| **发散式变化 (3.7)** | 一个模块因不同原因在不同方向上发生变化 | 拆分阶段(154)、搬移函数(198)、提炼函数(106)+提炼类(182) |
| **霰弹式修改 (3.8)** | 一种变化需要在许多不同类内做许多小修改，很难找、容易遗漏 | 搬移函数(198)、搬移字段(207)、函数组合成类(144)、内联函数(115)/内联类(186)+提炼 |
| **过长的消息链 (3.17)** | 连续请求多个对象形成长链，客户端与导航结构紧密耦合 | 隐藏委托关系(189)、提炼函数(106)+搬移函数(198) |
| **中间人 (3.18)** | 类的接口有一半函数都委托给其他类 | 移除中间人(192)、内联函数(115)、以委托取代超类/子类(399/381) |
| **内幕交易 (3.19)** | 两个模块私下大量交换数据 | 搬移函数(198)、搬移字段(207)、隐藏委托关系(189)、以委托取代子类/超类(381/399) |

### 2.5 数据相关

| 坏味道 | 说明 | 处理手法 |
|--------|------|----------|
| **可变数据 (3.6)** | 对数据的修改导致意料之外的 bug | 封装变量(132)、拆分变量(240)、将查询和修改分离(306)、以查询取代派生变量(248) |
| **全局数据 (3.5)** | 代码库任何角落都可修改，无法追踪改动源 | 封装变量(132)——首要防御手段，搬移到类/模块中限制作用域 |
| **基本类型偏执 (3.11)** | 用字符串代表电话号码、用数字代表钱——应为问题域创建有意义的基本类型 | 以对象取代基本类型(174)、以子类取代类型码(362)+以多态取代条件表达式(272) |
| **临时字段 (3.16)** | 类中某字段仅为特定情况而设，让人难以理解 | 提炼类(182)、搬移函数(198)、引入特例(289) |
| **纯数据类 (3.22)** | 只有字段和访问函数的数据容器，没有行为 | 封装记录(162)、移除设值函数(331)、搬移函数(198)将行为搬入、提炼函数(106) |
| **被拒绝的遗赠 (3.23)** | 子类不想或不需要继承超类的函数和数据 | 以委托取代子类(381)、以委托取代超类(399)、函数下移(359)、字段下移(361) |

### 2.6 其他

| 坏味道 | 说明 | 处理手法 |
|--------|------|----------|
| **异曲同工的类 (3.21)** | 两个接口不同的类做着相似的事 | 改变函数声明(124)、搬移函数(198)、提炼超类(375) |
| **注释 (3.24)** | 注释本身是一种香味，常被当作"除臭剂"使用。注释之所以存在是因为代码很糟糕 | 提炼函数(106)、改变函数声明(124)、引入断言(302)。需要写注释时先尝试重构，让注释变得多余 |

## 三、重构手法速查

> 详细动机、做法与代码示例见 [附录A](#附录a重构手法详解)。

### 3.1 提炼与内联

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 106 | **提炼函数** | 将意图与实现分开，以"做什么"命名（反向：内联函数(115)） |
| 115 | **内联函数** | 函数体比函数名更清晰时去除间接性（反向：提炼函数(106)） |
| 119 | **提炼变量** | 用命名良好的变量分解复杂表达式（反向：内联变量(123)） |
| 123 | **内联变量** | 变量名不比表达式本身更有表现力（反向：提炼变量(119)） |
| 124 | **改变函数声明** | 好名字一眼看出用途；参数应 ≤ 3，移除 Boolean 标记参数 |

### 3.2 封装

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 132 | **封装变量** | 所有可变数据，作用域超出单个函数就应封装 |
| 137 | **变量改名** | 好的命名是整洁编程的核心 |
| 162 | **封装记录** | 可变数据用类对象而非裸记录，隐藏结构细节 |
| 170 | **封装集合** | 提供添加/移除方法，取值函数返回副本而非原集合 |

### 3.3 搬移

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 198 | **搬移函数** | 函数频繁引用其他上下文，对自己上下文关心甚少——搬过去 |
| 207 | **搬移字段** | 字段与另一条记录耦合更紧密——搬过去 |
| 213 | **搬移语句到函数** | 调用某函数时总有相同代码每次都执行——合并进去 |
| 217 | **搬移语句到调用者** | 函数边界偏移，原本统一的行为需根据调用点不同而变化 |
| 222 | **以函数调用取代内联代码** | 已有函数能做的事不应再写一遍 |
| 223 | **移动语句** | 让相关联的代码靠得更近，为提炼函数做准备 |

### 3.4 重新组织数据

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 140 | **引入参数对象** | 一组数据总结伴同行（数据泥团），代之以一个数据结构 |
| 144 | **函数组合成类** | 一组函数形影不离地操作同一块数据 |
| 149 | **函数组合成变换** | 收拢所有计算派生数据的逻辑到一处 |
| 154 | **拆分阶段** | 一段代码同时处理两件事，用中转数据结构沟通 |
| 174 | **以对象取代基本类型** | 对数据的操作不仅局限于打印输出时，创建新类 |
| 178 | **以查询取代临时变量** | 将变量抽取到函数中，帮助函数分解 |
| 182 | **提炼类** | 一个类做了两个类的事 |
| 186 | **内联类** | 类不再承担足够责任，内联到使用最多的类中 |
| 189 | **隐藏委托关系** | `a.b.c` → 在中间人上创建委托方法 |
| 192 | **移除中间人** | 某类接口一半函数委托给其他类——直接和真正对象打交道 |
| 193 | **替换算法** | 用更清晰的算法替换复杂算法 |

### 3.5 简化条件逻辑

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 260 | **分解条件表达式** | 将条件判断和分支动作提炼为函数，突出逻辑结构 |
| 263 | **合并条件表达式** | 一连串条件检查最终行为一致时合并 |
| 266 | **以卫语句取代嵌套条件** | 只有一个分支是正常行为时用卫语句提前返回 |
| 272 | **以多态取代条件表达式** | 多个函数都有基于类型的 switch 时用多态；大部分情况只需 if/else |
| 289 | **引入特例** | 使用者都在检查某个特殊值（如 null）且处理方式相同时，用特例模式收拢 |
| 302 | **引入断言** | 告诉读者程序执行到此点时对状态的假设 |

### 3.6 简化函数调用

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 306 | **将查询和修改分离** | 任何有返回值的函数都不应有副作用 |
| 310 | **函数参数化** | 两个函数逻辑相似只有字面量不同时合并 |
| 314 | **移除标记参数** | Boolean 标记参数让你被迫阅读函数体才能知道它在做什么 |
| 319 | **保持对象完整** | 从记录导出几个值再传入 → 不如把整个记录传进去 |
| 324 | **以查询取代参数** | 函数自己也可获得的值不必由调用者传入 |
| 327 | **以参数取代查询** | 函数引用全局变量或欲搬移的元素时，使函数更独立 |
| 331 | **移除设值函数** | 字段值构造后不应改变时，不该提供 setter |
| 334 | **以工厂函数取代构造函数** | 需要根据环境或参数返回不同子类实例 |
| 337 | **以命令取代函数** | 函数太复杂需拆分且需追踪状态时封装为命令对象 |
| 344 | **以函数取代命令** | 命令对象只做一件事时简化为函数 |

### 3.7 处理循环与变量

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 227 | **拆分循环** | 一个循环做了两件不同的事，拆分后各自独立修改 |
| 231 | **以管道取代循环** | filter/map/reduce 帮助更快看清被处理的元素及处理动作 |
| 237 | **移除死代码** | 未使用的代码只会挡路，版本控制中有历史可查 |
| 240 | **拆分变量** | 变量承担多个责任时应分解（循环变量和收集变量例外） |
| 244 | **字段改名** | 数据结构是理解程序行为的关键 |
| 248 | **以查询取代派生变量** | 能被即时计算的变量应去掉，避免"源数据修改时忘记更新派生变量" |
| 252 | **将引用对象改为值对象** | 不可变对象可以放心传递给程序其他部分 |
| 256 | **将值对象改为引用对象** | 需要共享和统一更新时使用 |

### 3.8 继承与委托

| 编号 | 手法 | 一句话动机 |
|------|------|-----------|
| 350 | **函数上移** | 各子类函数体相同时提升至超类 |
| 353 | **字段上移** | 子类字段重复时提升 |
| 355 | **构造函数本体上移** | 子类构造函数有共同行为 |
| 359 | **函数下移** | 超类函数只与某子类有关 |
| 361 | **字段下移** | 某字段只被一部分子类使用 |
| 362 | **以子类取代类型码** | 通过子类实现多态处理条件逻辑 |
| 369 | **移除子类** | 子类变化被搬移走后失去价值 |
| 375 | **提炼超类** | 两个类在做相似的事 |
| 380 | **折叠继承体系** | 子类与超类差异太小 |
| 381 | **以委托取代子类** | 子类只复用超类行为但不愿支持其接口时，用组合代替继承 |

## 附录A：重构手法详解

> 本节精选 **17 种最常用手法**的动机、做法与代码示例。完整手法列表见第三章速查表（编号 106-399）。
>
> 示例使用 TypeScript，但这些模式适用于任何支持数据封装的语言。在不支持类的语言中，可用模块+闭包、record/struct 等机制等价实现。

### A.1 提炼函数（Extract Function, 106）

> 反向：内联函数(115)

**动机**：将意图与实现分开。函数一旦超过 6 行就开始散发臭味。

**做法**：创建新函数，以"做什么"命名 → 将代码复制到目标函数 → 只读变量作为参数传入，有赋值作为返回值 → 源函数中替换为调用。

```ts
// ❌ 反面：一个函数做多件事
function processOrder(order) {
  // 计算折扣...（10行）
  // 验证库存...（8行）
  // 生成物流单...（12行）
}

// ✅ 正面：每个函数一个意图
function processOrder(order) {
  const discount = calculateDiscount(order)
  validateStock(order)
  createShipment(order, discount)
}
```

### A.2 内联函数（Inline Function, 115）

> 反向：提炼函数(106)

**动机**：函数内部代码和函数名称同样清晰可读时，不需要多余的间接性。

```ts
// ❌ 反面：函数体比函数名更清晰
function getRating(driver) {
  return moreThanFiveLateDeliveries(driver) ? 2 : 1
}
function moreThanFiveLateDeliveries(driver) {
  return driver.numberOfLateDeliveries > 5
}

// ✅ 正面：内联后更直白
function getRating(driver) {
  return driver.numberOfLateDeliveries > 5 ? 2 : 1
}
```

### A.3 提炼变量（Extract Variable, 119）

> 反向：内联变量(123)

**动机**：复杂表达式难读时，用命名良好的局部变量分解。

```ts
// ❌ 反面：复杂表达式
return order.quantity * order.itemPrice -
  Math.max(0, order.quantity - 500) * order.itemPrice * 0.05 +
  Math.min(order.quantity * order.itemPrice * 0.1, 100)

// ✅ 正面：提炼变量
const basePrice = order.quantity * order.itemPrice
const quantityDiscount = Math.max(0, order.quantity - 500) * order.itemPrice * 0.05
const shipping = Math.min(basePrice * 0.1, 100)
return basePrice - quantityDiscount + shipping
```

### A.4 改变函数声明（Change Function Declaration, 124）

**动机**：函数名决定第一印象，参数列表阐述函数如何与外部共处。

**原则**：函数名 = 动词短语；参数 ≤ 3；移除 Boolean 标记参数；参数顺序：主要操作对象 → 辅助参数。

**迁移式做法（推荐）**：用提炼函数(106)创建新函数 → 逐步用内联函数(115)替换旧调用 → 全部替换后删除旧函数。

### A.5 封装变量（Encapsulate Variable, 132）

**动机**：所有可变数据，只要作用域超出单个函数，就应封装。

```ts
// ❌ 反面：暴露可变全局数据
let defaultOwner = { firstName: 'Martin', lastName: 'Fowler' }

// ✅ 正面：封装访问
let defaultOwnerData = { firstName: 'Martin', lastName: 'Fowler' }
export function defaultOwner() { return { ...defaultOwnerData } }
export function setDefaultOwner(arg) { defaultOwnerData = arg }
```

### A.6 引入参数对象（Introduce Parameter Object, 140）

**动机**：一组数据项总是结伴同行（数据泥团），应代之以一个数据结构。

```ts
// ❌ 反面：参数总是成组出现
function drawCircle(x: number, y: number, radius: number, color: string) {}

// ✅ 正面：引入参数对象
interface CircleParams {
  center: { x: number; y: number }
  radius: number
  color: string
}
function drawCircle(params: CircleParams) {}
```

### A.7 以对象取代基本类型（Replace Primitive with Object, 174）

**动机**：对某个数据的操作不仅局限于打印输出时，应创建新类。

```ts
// ❌ 反面：用字符串表达优先级，验证分散各处
orders.filter(o => o.priority === 'high' || o.priority === 'rush')

// ✅ 正面：值对象封装
class Priority {
  static LOW = 'low'; static NORMAL = 'normal'
  static HIGH = 'high'; static RUSH = 'rush'
  constructor(value) {
    if (!Priority.legalValues().includes(value)) throw new Error(...)
    this._value = value
  }
  higherThan(other) { /* 比较 */ }
}
orders.filter(o => o.priority.higherThan(Priority.NORMAL))
```

### A.8 以管道取代循环（Replace Loop with Pipeline, 231）

**动机**：管道操作帮助更快看清被处理的元素及处理动作。

```ts
// ❌ 反面：传统循环
const names: string[] = []
for (const e of employees) {
  if (e.salary > 10000) names.push(e.name)
}

// ✅ 正面：管道操作
const names = employees
  .filter(e => e.salary > 10000)
  .map(e => e.name)
```

### A.9 分解条件表达式（Decompose Conditional, 260）

**动机**：将条件判断和分支动作都提炼为函数，突出逻辑结构。

```ts
// ❌ 反面
if (date.before(SUMMER_START) || date.after(SUMMER_END))
  charge = quantity * winterRate + winterServiceCharge
else
  charge = quantity * summerRate

// ✅ 正面
charge = isSummer(date) ? summerCharge(quantity) : winterCharge(quantity)
```

### A.10 以卫语句取代嵌套条件（Replace Nested Conditional with Guard Clauses, 266）

**动机**：只有一个分支是正常行为时用卫语句，告诉读者"这种情况不是本函数核心逻辑所关心的"。

```ts
// ❌ 反面：嵌套条件
function getPayAmount(employee) {
  let result
  if (employee.isSeparated) {
    result = { amount: 0, reasonCode: 'SEP' }
  } else {
    if (employee.isRetired) {
      result = { amount: 0, reasonCode: 'RET' }
    } else {
      // 正常计算薪资...
    }
  }
  return result
}

// ✅ 正面：卫语句
function getPayAmount(employee) {
  if (employee.isSeparated) return { amount: 0, reasonCode: 'SEP' }
  if (employee.isRetired) return { amount: 0, reasonCode: 'RET' }
  // 正常计算薪资...
}
```

### A.11 将查询和修改分离（Separate Query from Modifier, 306）

**动机**：任何有返回值的函数都不应有副作用（命令-查询分离原则）。

```ts
// ❌ 反面：查询并修改
function getTotalAndSetAvailable(duration: number): number {
  const total = calculateTotal(duration)
  this.available = total > 0   // 副作用
  return total
}

// ✅ 正面：分离
function getTotal(duration: number): number {
  return calculateTotal(duration)
}
function setAvailable(duration: number): void {
  this.available = calculateTotal(duration) > 0
}
```

### A.12 移除标记参数（Remove Flag Argument, 314）

**动机**：Boolean 标记参数让你被迫阅读函数体才能知道函数在做什么。

```ts
// ❌ 反面：Boolean 标记参数
function deliveryDate(order, isRush: boolean) {
  if (isRush) { /* 加急处理 */ } else { /* 正常处理 */ }
}

// ✅ 正面：明确函数
function rushDeliveryDate(order) { /* 加急处理 */ }
function regularDeliveryDate(order) { /* 正常处理 */ }
```

### A.13 拆分变量（Split Variable, 240）

**动机**：变量承担多个责任时应分解。

```ts
// ❌ 反面：一个变量承担多种含义
let temp = 2 * (height + width)
temp = height * width   // temp 的语义变了

// ✅ 正面：各自独立的变量
const perimeter = 2 * (height + width)
const area = height * width
```

### A.14 以查询取代派生变量（Replace Derived Variable with Query, 248）

**动机**：能被即时计算的变量应去掉，防止"源数据修改时忘记更新派生变量"。

```ts
// ❌ 反面：存储派生数据
get discountedTotal() { return this._discountedTotal }
set discount(aNumber) {
  this._discount = aNumber
  this._discountedTotal = this._baseTotal * (1 - this._discount) // 需同步更新
}

// ✅ 正面：即时计算
get discountedTotal() { return this._baseTotal * (1 - this._discount) }
set discount(aNumber) { this._discount = aNumber }
```

### A.15 封装集合（Encapsulate Collection, 170）

**动机**：只封装变量访问但让取值函数返回集合本身是不够的。

```ts
// ❌ 反面：返回集合本身
get courses() { return this._courses }
set courses(aList) { this._courses = aList }

// ✅ 正面：封装添加/移除，返回副本
get courses() { return this._courses.slice() }
addCourse(aCourse) { this._courses.push(aCourse) }
removeCourse(aCourse) { /* 根据id或引用移除 */ }
```

### A.16 引入特例（Introduce Special Case, 289）

**动机**：使用者都在检查某个特殊值且处理方式相同时，用特例模式收拢。

```ts
// ❌ 反面：到处检查特殊值
if (aCustomer === 'unknown') customerName = 'occupant'

// ✅ 正面：特例对象
class UnknownCustomer {
  get name() { return 'occupant' }
  get isUnknown() { return true }
}
```

### A.17 引入断言（Introduce Assertion, 302）

**动机**：告诉读者程序执行到此点时对状态的假设。只检查"必须为真"，不用于外部数据校验。

```ts
applyDiscount(aNumber) {
  if (!this.discountRate) return aNumber
  console.assert(this.discountRate >= 0, '折扣率应 >= 0')
  return aNumber - this.discountRate * aNumber
}
```
