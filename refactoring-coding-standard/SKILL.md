## How to Use（触发与加载策略）
- **不带参数** — 默认加载 [决策速查表](cheatsheet.md) 作常规审查/重构指导（最快入口）。
- **带主题** — 如 `可变数据`、`过长函数`、`以多态取代条件表达式`：先查下方 [Topic Index](#topic-index) 与 [Chapter Index](#chapter-index) 定位，再读取对应章节。
- **带章节** — 如 `ch03`：直接载入对应章节文件。
- **浏览** — 问"有哪些章节"查看完整索引。

判断口径（加载阶梯，自上而下，命中即停）：
- [cheatsheet.md](cheatsheet.md) 可判定 → 只读 cheatsheet 作答。
- 超出 cheatsheet → 读 [patterns.md](patterns.md) 对应条目（61 项手法：何时用/怎么做/取舍）。
- patterns.md 不够（需动机/范例/反例细节）→ 载入对应章节（Chapter Index 定位）。
- 三者皆无（本书外框架/模式）→ 明说"本书未覆盖"，按 Fowler 原理迁移作答，不编造章节引用。
- 用户提出流行做法（Optional/策略模式/空对象模式等）→ 以 cheatsheet「流行做法 vs Fowler 立场」表为本，先判差再作答。

## 🔴 CHECKPOINT（作答纪律）
> 以下是防自主失控的强制停点；触达任何一处必须先停，再继续。

- 🔴 **作答前**：改动涉及公开 API / 跨多文件 / 大规模范围，或用户只问"要不要"——先给方案摘要与步骤，**等用户确认后再展开**；不改用户没让改的代码。
- 🔴 **每步后**：编译（或语言检查）→ 测试 → 提交；红条即回滚，换更小的步子。
- 🛑 STOP：**没有测试套件保护的代码，只给方案不动手**（用户明确要求直接改时例外）。

## 作答流程（5 步）
1. **理解请求**：读完代码/问题，先确认用户要的是"评估 / 给方案 / 动手改"哪一种（🔴 只问"要不要"时先给判断，不动手）。
2. **味道定位**：对照 [cheatsheet.md](cheatsheet.md)「坏味道 → 疗法」表找对应味；没有明显味 → 直接说明"不必改"及理由，不做过度重构。
3. **疗法定序**：按 cheatsheet「优先级判据」三轴（依赖顺序 → 风险梯度 → 价值/时机）定序；多疗法冲突时用"新旧并存（转发壳）+ 渐进迁移"降险。
4. **展开做法**：读 [patterns.md](patterns.md) 对应条目或对应章节（动机/做法/取舍俱在），产出**每步可验证**的方案。
5. **收尾**：附测试建议（ch04 自测试）与业务待确认点；明示哪些**没做**及为什么（YAGNI / 反例黑名单）。

## 「动手改」子流程（用户明确要求直接改代码时）
> 先用 5 步流程定方案，再按以下循环执行；无测试套件保护 → 🛑 按 CHECKPOINT 只给方案不动手（用户明确要求直接改时为例外，先补测试）。范围涉及公开 API/跨多文件/大规模 → 即使"直接改"也先给摘要等确认（CHECKPOINT 作答前）。

1. **基线**：先跑现有测试确认绿条；覆盖不足 → 先写暴露当前行为的测试并**确认它失败（预期红条——钉住行为；重构中途出现的红条才触发回滚）**。
2. **最小步**：每轮只做一个行为不变的小步（改名/提炼/管道化等，按疗法定序结果）。
3. **验证与提交**：编译/语言检查 → 跑相关测试 + 全量 → 全绿后 git 提交（与 CHECKPOINT「每步后」规则一致）；红条 → 回滚换更小步（cheatsheet 兜底表）。
4. **循环**：重复 2-3 到完成方案；任一步可回滚。
5. **收尾**：按轨 A 输出执行记录——③④ 用过去式写"做了什么 + 每步验证结果"，不是待办清单。

## 输出模板（按请求类型双轨）
> 每段先给结论再给依据。按请求类型选轨：
> - **评估/给方案型**（审查代码、要不要改）→ 轨 A ①-⑤；用户只要结论或判断题时只输出 ①。
> - **讲解型**（学/讲某重构手法或概念）→ 轨 B 四段。
> 代码形态：中间步骤给片段或动作描述，最终形态给完整代码块。
> **示例语言适配**：本书示例为 JavaScript；用户代码为其他语言时，改动后的代码用**用户语言**产出——机制翻译（map/reduce → 流/生成器、子类覆写 → 接口实现、工厂 → 构造器/静态方法），示例仅作机制说明；手法名沿用中文名，代码标识符遵循用户语言惯例。
> **多味/整文件**：② 按位置列出全部气味（不逐一展开）→ ③ 按优先级判据三轴产出**一条排序路径**（先低风险/无行为变化）→ ④ 共享测试与业务确认 → ⑤ 明示本轮**不做**的疗法及原因（避免一次性列全 = 过度重构）。

**轨 A（评估/给方案型）**
- **① 判定**：该改 / 不必改 + 一句理由（引用 ch03 味道名或 cheatsheet 条目名）。
- **② 证据**：坏味道 → 位置（函数/行/片段）→ 首选疗法（Ch 引用）；无味则列出"已排除的味"及排除依据。
- **③ 方案**：按优先级判据三轴定序的分步列表；每步 = 动作 + 验证方式（编译/测试/行为对比）；公开 API/跨文件步骤标 🔴 等确认。
- **④ 测试与业务确认**：先写哪些测试（含边界值，先红条确认），每步后的回归方式（ch04 自测试/风险驱动）；业务待确认点只列影响方案取舍的（对应作答流程第 5 步），能自行推断的（如常量命名）不问。
- **⑤ 未做与原因**：明示没改什么（YAGNI / 反例黑名单 / 超出范围 / 无测试套件只给方案不动手）。

**轨 B（讲解型）**
- **① 是什么**：手法名（中文 + English）+ Ch 出处 + 一句话定义。
- **② 何时用 / 何时不用**：适用信号（2-3 条）+ 明确"何时不用"的反例（引用黑名单/cheatsheet 兜底），反例至少 1 条。
- **③ 怎么做**：分步做法（每步动作 + 验证方式），至少一段前后对比片段。
- **④ 代价与落地**：取舍/间接性代价 + 测试建议（ch04）+ 书中案例位置（Ch §）。

## 反例黑名单（不要做什么）
> 以下反模式在 skill 多处提及，集中速查；命中即停。

- **单一 switch 不必动多态** — 多态有间接性代价，分支少且稳定时用数据表（ch10 / cheatsheet 兜底）
- **批量 null 判空特例化** — 需"重复模式足够清晰"，盲目推平掩盖差异（ch10）
- **没有测试套件就动手** — 🛑 只给方案不动手（CHECKPOINT）
- **改用户没让改的代码** — 公开 API / 跨多文件 / 大规模改动先给摘要等确认（CHECKPOINT）
- **为复用而预置灵活性** — YAGNI：只有"以后再重构很难"才预置（ch02）
- **声称"重构中代码两天不可用"** — 那是重写不是重构（cheatsheet 红条）
