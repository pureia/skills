# 第8章：搬移特性

## Core Idea
搬移组解决"东西放错了地方"：函数/字段/语句在模块间搬家，用管道取代循环，删死代码。模块边界重构的核心是"数据在哪，行为就该在哪"。

## Frameworks Introduced

### 搬移函数（Move Function）
- 动机：函数与所在模块格格不入（依恋情结、内幕交易）；或函数行为与某处数据/上下文走得更近
- 做法：① 检查函数的上下文：被谁调、调谁、用什么数据 ② 选择新宿主（持有最多函数所用数据的模块）③ 复制并最小化改动（用委托转发直到迁移完成）④ 改调用者 ⑤ 删除旧函数 ⑥ 测试；跨模块移动时注意特例（如递归、遍历）与私有成员的可见性
- 要点：判断"哪个模块拥有它使用的数据最多"

### 搬移字段（Move Field）
- 动机：字段在 A 处却总与 B 的数据一起变化/被 B 的函数更多地访问；或部分字段只在某些情况有意义
- 做法：① 检查字段被读写的所有地点 ② 在新宿主建字段 ③ 用新字段替换旧字段（可先复制+委托再删）④ 测试
- 排序策略：先搬字段，再搬使用它的函数

### 搬移语句到函数（Move Statements into Function）
- 动机：散在调用者身边的语句与某函数强相关，要消除重复/让函数完整
- 做法：① 确认要搬的语句汇集到一处（先移动语句）② 移植进目标函数 ③ 删除原语句 ④ 测试；若语句使用附近更多数据，也许应该反向（搬出）或提炼函数

### 搬移语句到调用者（Move Statements to Callers）
- 动机：函数中有些语句只对部分调用者适用（可选行为硬编码进被调函数）
- 做法：① 找出要搬的语句块 ② 从函数中剪掉（临时留空/占位，如空函数）③ 分别把所有调用者复制该语句 ④ 测试；多个调用者相同→考虑函数参数化

### 以函数调用取代内联代码（Replace Inline Code with Function Call）
- 动机：一串语句与已有函数功能重复
- 做法：① 确认已有函数的行为与这段代码等价 ② 判断功能：若使用现有 API 不贴切，先修改/新建函数 ③ 替换 ④ 测试

### 移动语句（Slide Statements）
- 动机：把相关代码放在一起，为提炼/合并创造条件
- 做法：① 检查移动是否安全（两个片段是否依赖同一变量、是否有副作用顺序问题）② 原地移动片段 ③ 测试；注意循环内移动的边界

### 拆分循环（Split Loop）
- 动机：一个循环里做了几件不同的事，可读性差、命名难（提炼信号）
- 做法：① 复制循环并只保留第一个关注点，删除其他 ② 第二个关注点建新循环 ③ 重复到每个关注点一个循环 ④ 测试
- 注意：不做"性能敏感的后悔"——多个循环也能合并回管道

### 以管道取代循环（Replace Loop with Pipeline）
- 动机：循环让"处理什么/怎么处理"看不清；函数一等公民时代用 map/filter/reduce
- 做法：① 建新管道，与循环逻辑平行 ② 逐步：把循环片段替换为管道运算符（filter/map），每次小步可测试 ③ 删除旧循环 ④ 测试
- 收益：元素与处理动作立刻可见

### 移除死代码（Remove Dead Code）
- 动机：无人调用的函数/字段/类/分支——注释、测试引用、条件分支都要查
- 做法：① 清理引用（含注释、异常分支、隐式反射调用）② 删代码 ③ 测试
- 要点：版本控制留着历史，没必要"留着备用"

## Mental Models
- **搬移方向 = 数据归属**：函数跟着最多的数据走；先搬字段再搬函数
- **搬移语句的两种方向**：聚拢到函数（消重）vs 散布到调用者（去条件化）——选择依据："这段语句对谁适用"
- **循环时代的结束**：管道是"意图"的语法；死代码没有保持成本以外的任何好处

## Worked Example
以管道取代循环：把 `for (const p of people) { if (p.age >= 18) adult.push(p.name); }` 改为 `const adult = people.filter(p => p.age >= 18).map(p => p.name);`——先加 filter 验证，再加 map 验证，最后删循环。

## Key Takeaways
1. 模块间搬移：先搬字段，再搬函数；用委托/壳保持每步可编译
2. 搬移语句到调用者：把"只对部分人适用"的语句放回调用者手中
3. 先移动语句把相似代码聚在一起，再进行提炼
4. 拆分循环不是性能顾虑——每个循环做一件事
5. 死代码即删，版本控制是它唯一的纪念物
