# 第2章：重构的原则

## Core Idea
重构（名词）= 对软件内部结构的调整，在不改变可观察行为的前提下提高可理解性、降低修改成本；重构（动词）= 用一系列重构手法调整结构。重构不是"大扫除"，而是把开发速度当作唯一目标的持续实践。

## Frameworks Introduced
- **两顶帽子（Two Hats）**：Kent Beck 的比喻——添加新功能（不修改既有代码）与重构（不添加功能）是两个不同状态，切换频繁但绝不混淆。
  - 何时用：任何时候要改代码之前先回答"我现在戴哪顶帽子"
  - 规则：重构时不加新测试（发现遗漏除外），只在处理接口变化时修改测试
- **三次法则（Rule of Three, Don Roberts）**：第一次直接做；第二次做类似的事会产生反感但忍了；第三次再做就该重构。事不过三，三则重构。
- **设计耐久性假说**：投入精力改善内部设计→增加软件耐久性→更长时间保持开发快速。
- **何时重构清单**：预备性重构（加功能前先让改动变容易）、帮助理解的重构、捡垃圾式重构、复审代码时重构、长期重构（Branch By Abstraction）。
- **重构与性能**：性能优化三分法——时间预算法（实时系统）、持续关注法（无效）、热点法（先度量→找热点→集中优化）。**先写出可调优的软件，然后调优它。**

## Key Concepts
- **可观察行为**：重构前后"用户关心的行为"不变；性能、接口签名可以变
- **published interface（已发布接口）**：所有者无权修改客户端代码的接口，妨碍重构
- **设计耐久性**：内部质量——易找到修改点、易理解、模块划分良好
- **Continuous Integration（持续集成）**：每天至少集成一次到主线，避免特性分支过长导致合并难度指数上升
- **代码所有制**：推荐团队代码所有制而非细粒度强所有制

## Mental Models
- **重构的每一步都很小 → 代码很少进入不可工作状态** → 可以随时停下
- **"速度"是重构的绝对理由**：重构唯一目的是更快开发，拒绝用"整洁代码"等道德理由论证
- **先令修改容易，再进行修改**（Kent Beck）：要加新功能做不好？先重构到容易，再添加
- **YAGNI 决策准则**：评估"如果以后再重构有多困难"，只有未来重构会很难时，才现在就添加灵活性机制

## Anti-patterns
- **把重构当作專门化的大计划**：绝大多数重构应是见机行事的，很少需要专门排期；"重构提交"强制与功能提交分离也多有争议
- **用"为未来做准备的参数/钩子"（夸夸其谈通用性）换取灵活性**：灵活性机制是收费的——增加当前复杂度、未来更可能被改错
- **持续关注式优化**：每处改动都只从一个狭隘的局部视角出发，90% 的优化工作是白费的
- **臆测性能瓶颈**：哪怕你完全了解系统（Ron Jeffries 教训），也要实际度量，不要臆测

## Worked Example
克莱斯勒综合薪资系统性能案例：大家推测多种性能瓶颈并讨论优化方案——全部猜错了。实际度量发现：一半时间用于创建"日期"实例，且这些实例只有几个相同值；进一步发现大量"日期区间"是空的。于是把空区间行为提炼为工厂函数，返回固定不变的"空日期区间"对象——系统速度提升近一倍，只花了约五分钟。教训：先度量，不要臆测。

## Key Takeaways
1. "我们重构时代码有两天不可用"——那做的就不是重构
2. 重构的时机：加新功能之前（预备性）、修复 bug 时、帮助理解代码时、复审时
3. 漂亮的代码也需要重构——权衡取舍随需求变化而变化
4. 重构不是银弹，是银钳子：帮助始终良好地控制代码
5. 性能：重构可能让代码变慢，但让优化阶段的性能调整更容易，且热点法需要良好结构支撑
