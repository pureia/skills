# 第9章：重新组织数据

## Core Idea
数据组解决"脏数据的可变性与派生"问题：拆分用途混杂的变量、字段改名、用查询替代派生数据，以及引用/值对象在正确语义间的切换。

## Frameworks Introduced

### 拆分变量（Split Variable）
- 动机：一个变量被多次赋值承载不同含义（循环变量是例外；累加累乘也是单一含义）
- 做法：① 找到被多次赋值的变量 ② 为每个"不同的含义"建立新变量 ③ 原名只用于第一个含义 ④ 后续含义各自独立声明 ⑤ 测试
- 边界：`i` 循环变量、`total` 累加器是正当的多次赋值——不要拆

### 字段改名（Rename Field）
- 动机：字段命名过时/含糊；重构中记录结构仍是对象，改名成本可控
- 做法：① 简单字段直接改并同步调用者 ② 公共 API 用迁移式：新字段+取值/设值函数转发旧字段 ③ 改所有调用点 ④ 删除旧字段 ⑤ 测试

### 以查询取代派生变量（Replace Derived Variable with Query）
- 动机：派生数据被缓存成变量（totalProduction、discountedTotal 之类），更新逻辑散落、易不同步
- 做法：① 找到被作为源修改的字段（删除设值路径）② 建查询函数在调用时计算 ③ 所有读点改用查询 ④ 测试；性能敏感区可复核缓存，其余一律查询
- 要点：`addProducer` 只更新源字段 `producers`，派生值实时算

### 将引用对象改为值对象（Change Reference to Value）
- 动机：小对象（钱、日期区间）不可变更好；引用语义造成"多处改一处"的坑
- 做法：① 确认对象行为对称（equals/hashCode）② 把 setter 改为整体赋值 ③ 测试
- 收益：更新=替换（`new`），而非"找到所有引用逐处改"

### 将值对象改为引用对象（Change Value to Reference）
- 动机：对象很大、共享实例有意义（人员、组织），每次复制带来身份与内存问题
- 做法：① 建仓储（repository）② 对象从仓储获取（以 ID 关联）③ 处理相等性（保持单一实例）④ 更新构造/工厂 ⑤ 测试
- 决策准则：**值 vs 引用 = 数据是否值得共享**；小且无身份→值，大且需要身份→引用

## Mental Models
- **可变性是最贵的东西**：能算出来的别存着；存了就保证"仅一处定义"
- **名字要承载单一含义**：多用途变量（如 `result` 在不同阶段复用）应拆分
- **值/引用选择**：货币、日期→值对象；客户、账户→引用对象

## Worked Example
`Province` 类：`_totalProduction` 在 `constructor` 与 `addProducer` 两处手动累加。重构：删除 `_totalProduction` 字段与手动更新，`get totalProduction()` 改为 `this._producers.reduce((sum, p) => sum + p.production, 0)`；`addProducer` 只管 push；测试 shortfall/profit 依然通过——派生数据只有一处来源。

## Key Takeaways
1. 拆变量：每一种不同含义一个变量；循环变量/累加器例外
2. 字段改名：内部直接改，公开 API 用迁移式转发
3. 派生值一律以查询取代——除非度量证明缓存必要
4. 值对象不可变可整体替换；引用对象经仓储共享身份
5. 先明确"谁拥有该数据"，再决定值/引用语义
