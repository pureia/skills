# 第3章：代码的坏味道（24 种）

## Core Idea
本章给出 24 种代码坏味道（bad smell）作为重构的雷达信号：不是缺陷清单，而是"闻到这个味道就该想到这些重构手法"的索引。每种味道都对应一个或多个人称"疗法"的重构。

## Frameworks Introduced
- **坏味道 → 疗法的两类对应**：每一节都是"症状 → 首选重构→ 变体处置"。遇见坏味道时用 Ch13 速查表整体对照。

## Key Concepts（24 种坏味道一览）
- **神秘命名（Mysterious Name）**：命名不清 → 改变函数声明、变量改名、字段改名；想不出好名字往往意味着更深的设计问题（ch3.1）
- **重复代码（Duplicated Code）**：同一类两处相同表达式→提炼函数；相似但不相同→先移动语句再提炼；不同子类间→函数上移（3.2）
- **过长函数（Long Function）**：长函数最难改；99% 用提炼函数；参数/临时变量阻碍时先以查询取代临时变量、引入参数对象、保持对象完整；终极武器是以命令取代函数（3.3）
- **过长参数列表（Long Parameter List）**：以查询取代参数、保持对象完整、引入参数对象、移除标记参数；多个函数共享参数→函数组合成类（3.4）
- **全局数据（Global Data）**：任何角落可改、无法溯源 → 封装变量，再把函数/数据搬进模块收窄作用域（3.5）
- **可变数据（Mutable Data）**：一处更新、别处期望不同值 → 封装变量、拆分变量、移动语句+提炼函数分离副作用、查询与修改函数分离、移除设值函数、以查询取代派生变量；限制可修改代码量→函数组合成类/变换、改引用对象为值对象（3.6）
- **发散式变化（Divergent Change）**：同一个模块因不同原因在不同方向变化 → 拆分阶段、搬移函数、提炼函数、提炼类（3.7）
- **霰弹式修改（Shotgun Surgery）**：与发散式相反——一种变化要散布在多类中做小修改 → 搬移函数/字段聚拢、函数组合成类/变换、拆分阶段、内联函数/内联类（3.8）
- **依恋情结（Feature Envy）**：函数与别模块数据交互远超自身模块 → 搬移函数（"哪个模块拥有所用数据最多，就放哪"）；GoF 策略/访问者模式属于抗发散式变化的例外（3.9）
- **数据泥团（Data Clumps）**：总是同时出现的数据项 → 提炼类+引入参数对象/保持对象完整；删掉一项后其余失去意义，就是该建对象了（3.10）
- **基本类型偏执（Primitive Obsession）**：钱、坐标、范围用基本类型 → 以对象取代基本类型；类型码→以子类取代类型码+以多态取代条件表达式；"类字符串类型"(stringly typed)变量是重灾区（3.11）
- **重复的 switch（Repeated Switches）**：多处以同一条件做相同分支 → 以多态取代条件表达式（3.12）
- **循环语句（Loops）**：可读性差 → 以管道取代循环（filter/map 等）（3.13）
- **冗赘的元素（Lazy Element）**：名字即实现/空壳函数类 → 内联函数、内联类；继承体系内→折叠继承体系（3.14）
- **夸夸其谈通用性（Speculative Generality）**：为"总有一天需要"加的钩子/参数/抽象 → 折叠继承体系、内联函数/类、改变函数声明；唯一用户是测试用例→删测试+移除死代码（3.15）
- **临时字段（Temporary Field）**：仅特定情况才用到的字段 → 提炼类+搬移函数；"变量不合法"场景→引入特例（3.16）
- **过长的消息链（Message Chains）**：a.getB().getC().getD() → 隐藏委托关系；更好：提炼函数把用链的模式放进去再搬移；有人把任何函数链都视为坏味道——不赞成（3.17）
- **中间人（Middle Man）**：一半接口都在委托 → 移除中间人；只用少数字段→内联函数；其他行为→以委托取代超类/子类（3.18）
- **内幕交易（Insider Trading）**：模块间大量私下交换数据 → 搬移函数/字段、隐藏委托关系；继承密谋→以委托取代子类/超类（3.19）
- **过大的类（Large Class）**：字段/代码太多 → 提炼类（相同前缀/后缀的变量是信号）、提炼超类、以子类取代类型码；观察使用者只用到的功能子集（3.20）
- **异曲同工的类（Alternative Classes with Different Interfaces）**：应可替换但接口不一致 → 改变函数声明统一签名、搬移函数对齐协议、提炼超类补偿重复（3.21）
- **纯数据类（Data Class）**：只有字段+访问函数 → 封装记录、移除设值函数、搬移函数/提炼函数把行为搬进来；例外：不可变的中转数据结构（拆分阶段产物）无须封装（3.22）
- **被拒绝的遗赠（Refused Bequest）**：子类不想继承 → 传统疗法（函数下移/字段下移到兄弟类、超类抽象化）只在引起困惑时才用；拒绝接口而非实现时味道浓烈→以委托取代子类/超类（3.23）
- **注释（Comments）**：注释是香味，但常被当除臭剂 → 需要注释解释做什么→提炼函数；解释行为→改变函数声明改名；说需求规格→引入断言（3.24）

## Mental Models
- **坏味道不是 bug，是"改动用最少的功夫、但可能引入 bug"的信号**：凌乱代码不必都改——只有需要修改、需要理解时才值得
- **发散式 vs 霰弹式**："一个类因多种原因变化" vs "一种变化散布多个类"——同为耦合问题的两面
- **味道按"变化的方向"分类**：命名、重复、过长、耦合（依恋/内幕/消息链）、数据（全局/可变/泥团/基本类型）、条件与循环、继承滥用

## Anti-patterns
- **把注释当成除臭剂**：代码糟才需要注释；先重构让注释多余
- **无条件反对条件语句**：真正的敌人是"重复的 switch"，不是所有条件逻辑
- **把所有函数链都当坏味道**：冷静镇定地判断——过度隐藏也会制造中间人
- **把 switch 全换多态**：多态是有代价的（多一层间接性），只对重复的分支选择动刀

## Worked Example
过大的类处理路径：看到 `depositAmount`/`depositCurrency` 同前缀字段 → 提炼类→ 在新类中找依恋情结 → 把行为搬进新类 → 数据泥团找到归宿，新对象的"小社会"开始散发芳香。
过长函数处理路径：先加注释→注释提示语义距离→提炼；参数太多→以查询取代临时变量→引入参数对象→以命令取代函数。

## Key Takeaways
1. 看到以下特征直接联想疗法：重复→提炼；过长→注释定位+提炼；参数多→对象化/查询化；类型码 switch→多态
2. 改动前先想"这个味道对应哪种变化方向"，再选 Ch13 速查表中的重构
3. 一次修复不一定一位疗法：先内联聚拢、再提炼拆分是常见组合
4. 味道清单是记忆索引——真实代码要结合上下文判断气味强弱
