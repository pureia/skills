# 第12章：处理继承关系

## Core Idea
继承组在抽象层次间搬运（上移/下移）、用子类别化类型码、用委托取代不应共享的继承。核心判断：**继承是"是"关系（接口+实现共享），委托是"包含"关系——用错继承时果断改委托。**

## Frameworks Introduced

### 函数上移（Pull Up Method）
- 动机：各子类有相同函数（真正的重复代码）→提升到超类
- 做法：① 确认函数在子类中一致（不一致先移动语句/公共辅助函数对齐）② 在超类中加函数 ③ 删除子类副本 ④ 测试；子类做不同细节→用模板方法（超类主流程+子类具体化）

### 字段上移（Pull Up Field）
- 动机：子类有相同字段（尤其双方都要引用同一数据）
- 做法：① 检查字段的所有使用 ② 若只在子类用，先下移/替换（构造参数直达）③ 把字段移到超类 ④ 测试

### 构造函数本体上移（Pull Up Constructor Body）
- 动机：子类构造函数前半部分相同（先 super 后子类字段）
- 做法：① 确认子类都可共享该部分代码 ② 把公共本体上移到超类构造函数 ③ 调整子类构造参数（用参数对象减少参数）④ 测试

### 函数下移（Push Down Method）
- 动机：超类函数只对某子类有意义；超类抽象化前清理
- 做法：① 在子类中复制原函数，删除超类定义 ② 测试；两步走避免接口断裂（可选：先留存转发壳）

### 字段下移（Push Down Field）
- 动机：字段只被部分子类使用
- 做法：① 找到字段只在哪个子类用到，先声明到该子类 ② 公共引用点保留间接访问 ③ 测试 ④ 删超类字段

### 以子类取代类型码（Replace Type Code with Subclasses）
- 动机：以字符串/数字类型码驱动条件行为；类型码有"一组可能的变体"语义
- 做法：① 确定一个有限的状态/变体集合 ② 建子类（工厂函数按码返回子类型）③ 逐个把多态相关行为下移；把条件分支替换为虚函数覆写 ④ 逐类测试
- 注意：分支已很小且稳定时不必子类化

### 移除子类（Remove Subclass）
- 动机：子类只剩一点点不同/一个子类永远用不到（多余结构）；或委托取代后子类消亡
- 做法：① 把子类行为折叠进超类 ② 删除子类 ③ 工厂返回超类 ④ 测试

### 提炼超类（Extract Superclass）
- 动机：两个类有许多共同字段/方法（重复代码、异曲同工）；"是"关系成立
- 做法：① 建抽象超类 ② 上移字段 ③ 上移方法 ④ 重复（编译-测试）⑤ 考虑推平整：不强制每个子类都用超类的所有东西（超类可含默认值/空白实现）
- 替代路径：两个类太独立→合并成"组合"（委托）而非继承

### 折叠继承体系（Collapse Hierarchy）
- 动机：超类与子类差异不再有意义（子类被抽干/超类无特别意义）
- 做法：① 把子类剩余的行为搬到超类 ② 删除子类 ③ 修改构造/工厂 ④ 测试

### 以委托取代子类（Replace Subclass with Delegate）
- 动机：子类继承"实现"却拒绝"接口"（被拒绝的遗赠）；或"包含关系"比"是关系"更适合（对象的多变维）
- 做法：① 为被委托的子类/对象的可变部分建委托字段 ② 委托类型持有该行为（类 + 转发函数）③ 修改超类/接口改为聚合 ④ 测试；例子：经理 vs 雇员——角色用委托，身份用继承
- 时机：子类与超类只有部分共享；两维度同时变化（如"人员 × 是否退休"）应委托

### 以委托取代超类（Replace Superclass with Delegate）
- 动机：超类只有部分行为需要，但接口把所有行为都暴露（拒绝接口）；或"组合胜过继承"
- 做法：① 把超类的有用行为聚合进新字段 ② 建立转发函数（满足需要的接口）③ 删除继承关系 ④ 测试
- 收益：只暴露需要的行为，别的接口不再泄露

## Mental Models
- **"是" vs "包含"**：`Manager` is-a `Employee` 成立但会引入老板们不需要的接口时，改用"Manager holds Employee"
- **类型码→多态→子类/委托的演进**：重复的 switch → 以子类取代类型码 → 多态；变体持续增加或多维变化→委托
- **抽象类不强制空实现**：传统"超类必须抽象"的教条并非常态；拒绝继承实现没关系，拒绝继承接口才是问题

## Worked Example
以委托取代子类：`Booking` 基类与 `PremiumBooking` 子类（premium 只改变部分行为）。重构为：`Booking` 成员内含 `premiumDelegate`（惰性创建），`hasPremium() => this._premiumDelegate`、"加价部分"的方法由委托对象实现，`Booking` 覆写时先查委托。逐步：① 建委托对象 ② Booking 中保留 delegate 字段 ③ 把子类特有逻辑移入委托 ④ 预览 "booking 不再是 premium" 的场景随时代变化——委托使维度拆分成为可能。

## Key Takeaways
1. 同样的函数/字段在子类中→上移；只在部分子类使用→下移
2. 类型码 + switch → 子类化 → 多态；分支增多/多维 → 委托
3. 子类抽干→折叠；超类太大→提炼超类或改委托
4. 继承用于共享接口+实现；只共享无关细节 → 用委托
5. 构造函数公共段上移，用参数对象收窄参数
