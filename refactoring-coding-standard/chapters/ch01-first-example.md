# 第1章：重构，第一个示例

## Core Idea
用一个"戏剧演出团打印账单"的完整示例演示重构全过程：重构前先有测试，然后以"提炼函数—移除局部变量—拆分阶段—多态"的次序小步改造，每步编译、测试、提交。核心教益是：**重构是一连串微小步骤，不是一次大手术。**

## Frameworks Introduced
- **重构的节奏（编译·测试·提交）**：每完成一次微小的行为保持修改，立即编译→运行测试→提交到本地版本控制。
  - 何时用：任何一次重构之后
  - 为什么：犯错时只需检查很小的改动范围；版本控制提供失败回滚点
- **提炼函数（Extract Function, 106）**：把一段代码抽成独立函数，用它的"做什么"命名。
  - 何时用：看到注释、switch 分支、循环等语义单元时
  - 前置：先移除不必要的局部变量，让提炼简单
- **以查询取代临时变量（Replace Temp with Query, 178）**：把临时变量改成函数调用，消除局部作用域阻碍。

## Key Concepts
- **可观察行为**：重构不得改变用户可观察的行为；无关紧要的内部状态（如函数调用栈）可以变
- **两顶帽子**：添加新功能 vs 重构是两种状态，不能同时做
- **语义距离**：函数"做什么"与"如何做"之间的距离，是判断是否该提炼的依据

## Mental Models
- **先把理解搬进代码**（Ward Cunningham 的灵光）：读代码时脑海中转瞬即逝的理解，提炼为函数/命名，防止遗忘
- **小步修改 = 快速反馈**：改动越多，一旦犯错就越难定位；小步是防止混乱的关键
- **需要"改"才重构**：如果代码能正常工作且不会再被修改，就没必要重构；需求变化使重构必要

## Anti-patterns
- **复制整个函数来满足变体需求**：导致重复逻辑，未来一处修改两处同步，修改点越来越多、错误机率大增
- **一次性添加大量功能后再测试**：这正是重构节奏要避免的

## Worked Example
需求两个变化：① 输出 HTML 账单 ② 计费规则+积分规则要变（演出类型会扩展）。Fowler 的做法：
1. 先写测试：创建若干 invoice 作为输入，将输出与手工核对过的字符串比较（自我检验）
2. 提炼 `amountFor(perf, play)` 取出 switch 计费块；将 `thisAmount` 改为 `result` 并重命名参数为 `aPerformance`
3. 移除局部变量 `play`（提炼 `playFor`，再内联变量），使 `amountFor(aPerformance)` 只剩一个参数
4. 内联 `thisAmount` 临时变量；把"计算"函数们搬出 `statement`，定义 `renderPlainText`（阶段一：计算）
5. 创建 `renderHtml`（阶段二：格式化），中间用不可变数据对象沟通
6. 按类型拆出 `PerformanceCalculator` 子类（tragedy/comedy），把 `amount` 与 `volumeCredits` 计算函数下移；`statement` 只负责把 invoice 灌进计算器
7. 最终 `statement` 收敛为 3~4 行的"工厂+两个 render 函数"；每次独立改动后可随时停下

## Key Takeaways
1. 重构前必须有可靠的、自我检验的测试——没有测试就不要动代码
2. 先消除局部变量（用查询/内联），再提炼，提炼就会简单得多
3. 每步都要编译、测试、提交；失败就回滚，用更小的步子重来
4. 重复/带注释的代码是提炼的天然信号
5. 拆分阶段 + 多态是应对"两个变化方向"的标准策略（先分阶段，再用类型组织计算）
