# 第7章：封装

## Core Idea
封装组关注"数据与控制访问"：用记录/集合/类等结构把裸露的数据与临时变量包起来，收窄修改路径，把委托关系显式化。

## Frameworks Introduced

### 封装记录（Encapsulate Record）
- 动机：嵌套的记录结构（JSON 字面量）被多处直接读写，改名/改逻辑要散布所有访问点
- 做法：① 把记录包裹成类 ② 给每字段加取值/设值函数 ③ 把嵌套记录递归封装（或有选择）④ 测试；只读字段不做设值函数，可配合以查询取代辅助
- 要点：这是纯数据类的第一步疗法

### 封装集合（Encapsulate Collection）
- 动机：暴露集合本身的 getter 让外部直接 `add/remove`，收集到的修改行为无法控制
- 做法：① 加取值函数返回只读视图（副本/不可变包装）② 加 add/remove 方法 ③ 把外部直接修改调用点改为新方法 ④ 测试
- 要点：getter 永不返回内部集合的可修改引用——只读代理或副本

### 以对象取代基本类型（Replace Primitive with Object）
- 动机：价格/温度/电话/坐标等被当作基本数字或字符串裸用（"类字符串类型"）
- 做法：① 建值对象（含构造与取值函数）② 修改旧数据引用为对象 ③ 把对这个值的行为（转换、显示、比较）加进对象 ④ 测试
- 收益：一堆散落的行为随之聚拢，如显示逻辑、单位换算

### 以查询取代临时变量（Replace Temp with Query）
- 动机：临时变量污染作用域、阻碍提炼
- 做法：① 确认变量被赋值一次且赋值表达式无副作用（有副作用→先拆分变量）② 建函数返回值 ③ 原地替换变量 ④ 测试
- 收益：函数内所有访问点共享"查询"，提炼时参数更少（见 ch01 的 `playFor`）

### 提炼类（Extract Class）
- 动机：类里有部分字段+方法总在一起变化，或某组字段只在部分时刻使用（临时字段、过大的类）
- 做法：① 决定拆分哪部分 ② 建新类 ③ 搬移字段、搬移方法 ④ 测试 ⑤ 调整既有对象的调用点/引用
- 决策信号：同前缀/后缀的字段组、只被一个子集使用者的功能子集

### 内联类（Inline Class）
- 动机：类失去独立价值（只剩一个函数；或该类角色的特殊职责都不复存在）
- 做法：① 识别要内联的类 ② 逐项把字段与方法搬进接收方 ③ 更新调用者 ④ 删除旧类 ⑤ 测试

### 隐藏委托关系（Hide Delegate）
- 动机：过长的消息链、客户与远隔对象耦合
- 做法：① 在想接收的对象上加委托方法（封装 getter 链）② 原有调用者改为调用委托方法 ③ 测试
- 收益：导航结构变化时客户端无感（管理者-秘书模式）

### 移除中间人（Remove Middle Man）
- 动机：过度委托——一半接口都只是转发（中间人味道）
- 做法：① 找到被委托的对象 ② 在客户端直连被委托对象或删除委托方法 ③ 更新调用者 ④ 测试
- 决策：委托方法个数与"是否真的增加了价值"比照；隐藏委托与移除中间人是两极，靠嗅觉平衡

### 替换算法（Substitute Algorithm）
- 动机：换个更清晰/更贴近需求的算法
- 做法：① 以新算法准备一个函数 ② 让旧函数调用新函数 ③ 编译+测试 ④ 删旧算法；fizzbuzz 式比较两个算法的输出更稳
- 要点：先小步替换，再清扫，而不是一大步重写

## Mental Models
- **封装 = 收窄修改路径**：所有修改都经过为数不多的函数，才能监控、演进、加断言
- **getter 的诚实性**：对外暴露的集合必须是不可变的——否则封装形同虚设
- **委托的太极**：隐藏委托 vs 移除中间人，是"耦合要收"与"间接层要减"之间的天平

## Worked Example
封装集合：`const orders = new Set(); get orders() { return this._orders; }` 被外部 `orders.add(...)`；改为 `get orders() { return this._orders.slice(); }` + `addOrder(x)`/`removeOrder(x)`，把外部 3 处 `add` 改为 `addOrder`，测试确认内部集合无法再被外部直接改动。

## Key Takeaways
1. 类变量/单例/全局数据的第一反应：封装变量
2. 集合永不裸返；记录层级封装
3. 临时字段→提炼类；中间人→移除中间人；消息链→隐藏委托
4. 算法替换：先并存后删除，输出对比
