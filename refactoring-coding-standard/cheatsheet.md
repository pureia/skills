# 决策速查表（cheatsheet.md）

> 面向"现在该做什么"的决策辅助，**本技能的唯一决策入口**。术语定义见 [glossary.md](glossary.md)，手法细节见 [patterns.md](patterns.md) 与 `chapters/ch06–ch12`。

## 何时动手
| 情况 | 行动 |
|---|---|
| 加新功能前发现结构不便修改 | 先重构（预备性重构），再添加 |
| 读代码需要反复琢磨"它在做什么" | 立刻提炼/改名（帮助理解的重构） |
| 发现简单垃圾 | 顺手清理（捡垃圾式） |
| 修复 bug 前的根因研究 | 顺带消除重复/合并逻辑（降低复发） |
| 代码不再被修改、没人需要理解 | 不要重构 |
| 重写比重构更容易 | 重写（需经验判断） |
| 团队长期忽略重构 | 才值得安排有计划的专门重构 |

## 🔴 实施安全协议（红条规则）
- 测试失败（红条）时**不许重构**；先"回退到绿条"。
- 重构 = 每步编译（或语言检查）→ 测试 → 提交；失败则回滚换更小的步子。
- 重构不是重写：声称"重构中代码两天不可用"的，做的不是重构。
- **情况越复杂，步子越小**：复杂改动拆成更多、更小的可验证步骤。

## 失败模式 → 兜底（if-X 失败 → Y）
> 触发任何一行的"症状"先做「一线修复」；仍不行走「兜底」。判断口径：有回滚通道的永远先回滚。

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| 提炼时想不出好名字 | 停止提炼，或用字面描述临时命名后继续 | 内联回去——想不出名字往往说明不该提炼 |
| 没有测试，或测试红条 | 先写暴露当前问题的测试（红条确认） | 退回绿条版本，换更小步子的重构路径 |
| 步骤后行为变化（测试过但结果不对） | 立即回滚到上一个可验证版本 | 用拆分阶段/新旧并行对比定位差异，再选路径 |
| 目标是公开 API / 找不到全部调用者 | 新签名 + 旧函数薄壳转发（迁移式改名） | 逐个迁移调用者完成后再删旧壳，绝不一步到位 |
| 提炼的代码段要返回多个被赋值变量 | 以查询取代临时变量 / 拆分变量，先简化 | 放弃本次提炼，先做准备工作再回来 |
| 类型码分支少且稳定（单一 switch） | 不动——多态有间接性代价，行为差异小时用数据表 | 分支持续增长且重复出现时，才以多态取代条件表达式 |
| 担心重构伤性能 | 先度量找热点（90% 时间在 10% 代码） | 优化热点并重新度量，重建后再谈预优化 |
| 条件里只有一支是特例（早退） | 卫语句取反早退 | 各分支平等 → 保持链，不卫语句化 |
| 子类拒绝父类接口 | 函数下移 / 字段下移 | 仍痛 → 以委托取代子类 / 超类 |
| 数据泥团删一项后其余失去意义 | 提炼类 + 引入参数对象 | 保持对象完整，传整个对象而非继续拆参数 |

## 优先级判据（多坏味道/多疗法冲突时谁先谁后）
> 三条轴合成，**自上而下先满足**；用于多个疗法指向冲突时定序。

- **① 依赖顺序**：先搬字段再搬函数；先移除局部变量再提炼；先清理死代码再重构；新签名 + 旧壳转发 → 逐个迁移 → 删旧。
- **② 风险梯度**：先做低风险、无行为变化的（改名、提炼、移除死代码），再碰高风险（改变函数声明、重构 API、继承与委托改造）；每小步可回滚。
- **③ 价值/时机**：优先解决"阻碍当前加功能"的结构问题（预备性重构）＞帮助理解＞捡垃圾＞复审＞长期重构（Branch By Abstraction）。**YAGNI**：只有"以后再重构很难"才预置灵活性。

**冲突裁定**：若价值/时机要求冒险，用"新旧并存（转发壳）+ 渐进迁移"降低风险，而非一步到位；三轴同向时按序执行最稳。

## 决策规则
| 决策 | 判据 | ch |
|---|---|---|
| 函数归属 | 谁使用该函数的数据最多，就把函数放谁那（依恋情结解法） | ch08 |
| 类拆分 | 同前缀/后缀的字段组 → 提炼类候选；某子集功能只被一类客户用 → 候选 | ch07 |
| 值 vs 引用 | 小、无身份、需整体替换 → 值对象；大、需共享身份 → 引用对象（仓储） | ch09 |
| 继承 vs 委托 | 共享"接口+实现"→继承；只复用实现或拒绝接口 → 委托 | ch12 |
| 卫语句 vs if/else | 一个分支是特例（主线之外）→卫语句；各分支平等 → 链 | ch10 |
| 命令 vs 函数 | 函数参数/状态复杂、需要分步执行 → 命令；否则函数 | ch11 |

## 流行做法 vs Fowler 立场
> 社区替代方案常被误当等价；以下按第 2 版立场引用，回答时以本书原意为准，不要把流行说法当成 Fowler 立场。

| 流行做法 | Fowler 立场（第 2 版） | ch |
|---|---|---|
| `Optional.orElse()` / 真值链收敛空值 | 卫语句就是标准形态；只有"重复模式足够清晰"才引入特例 | ch10 |
| 空对象模式（Null Object） | 第 2 版称「引入特例」；特例可以是类/记录/transform 包装，不限于类 | ch10 |
| 策略模式（Strategy）用于类型分派 | 行为随状态切换 → 用策略；类型固定、同一条件多处判 → 用多态 | ch10, ch12 |

## 阈值与默认值
- 函数超过 ~6 行开始散发臭味；继续分解，哪怕只有 1 行。
- 三次法则：同款代码第三次 → 重构。
- 一句话函数：名字比实现长没关系（highlight→reverse 案例）。
- 测试频率：当前代码相关测试每几分钟一次；全量每天至少一次。
- 每遇到一个 bug：先写暴露它的测试，通过才算修完。
- 派生数据：一律查询实时计算，除非度量证明缓存有必要。
- 全局数据：少量可容忍但一律封装；越多越危险。

## 战术提醒
- 两步走：先"移除局部变量"再"提炼"；先"搬移字段"再"搬移函数"。
- 拆分阶段：中间结构不可变；一阶段一上下文。
- 性能：先度量找热点，再优化热点；每次优化后重新度量。
